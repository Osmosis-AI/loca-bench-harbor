# loca-bench-harbor

Generated Harbor tasks for [LOCA-bench](https://github.com/hkust-nlp/LOCA-bench),
one Harbor task per upstream configuration entry
(15 families x 7 EDL levels x 5 seeds = 525).

Task artifacts are generated by `Osmosis-AI/harbor` under `adapters/loca-bench`. Do not hand-edit `tasks/`, `registry.json`, or `manifests/`; CI validates them with the exact adapter commit recorded in their manifest. Release tooling and documentation live in this repository.

## Status

The manifest records harness `1.3.0+loca.8b6fac49` and the same 525 upstream task configurations as `v1.2.1`.

The runtime adds native OpenAI Responses with complete reasoning and function-call state replay, while retaining Chat Completions. API format is selected independently of reasoning effort. Use the matching Harbor controller from [Harbor PR #21](https://github.com/Osmosis-AI/harbor/pull/21) or a later commit containing it. Updating Harbor alone cannot add Responses support to the older task images.

Task content, scoring rules, per-EDL timeouts, and the existing ReAct profile remain unchanged from `v1.2.1`. Earlier tags remain immutable. `v1.1.0` and `v1.0.0` use the earlier grading semantics and are not comparable across the model-caused API termination change introduced in `v1.2.0`.

Dataset `1.4.0` is being prepared for agent `2.0.0`, runtime contract `2`, profile `loca-hardened-react-v2`, and isolation policy `landlock-seccomp-v1`. It requires a matching Harbor controller and a newly built runtime image. The existing generated tree still pins `v1.3.0`; no hardened image digest or `v1.4.0` dataset has been published by this change. Dataset versions identify task bundles independently of the agent and runtime contract versions. Report the hardened profile separately from earlier scores because it changes access to private grading and service state.

## Layout

```
registry.json                     seven dataset entries; task items are {name, path}
tasks/<task_id>/                  task.toml, instruction.md, tests/test.sh, environment/Dockerfile
manifests/loca-bench-<version>.json  upstream pin, runtime image digest, matrix
```

## Datasets

`loca-bench` 525, `loca-bench-core` 225, `loca-bench-8k` / `-64k` / `-128k` /
`-256k` 75 each, `loca-bench-smoke` 8.

## Consuming

```bash
harbor run --repo Osmosis-AI/loca-bench-harbor@v<version> --dataset loca-bench@<version>
```

Registry task entries carry only `name` and `path`; Harbor binds `git_url` and
the resolved commit at resolve time. The platform sets
`harbor_repo="Osmosis-AI/loca-bench-harbor@v<version>"` and
`harbor_dataset="loca-bench@<version>"`.

## Release procedure

The order is one-way. Never generate against a mutable tag, reuse an old runtime digest for a changed adapter, or move an existing release tag.

1. Merge the final Harbor adapter source into `adapters`, then release the runtime image from that committed source using its `loca-runtime-<sha12>` tag workflow. `.github/workflows/loca-bench-runtime-image.yml` builds linux/amd64 and linux/arm64 natively and runs the complete Docker runtime suite, including the isolation probes, on each candidate digest. Both architectures must pass without skipped tests before the multi-arch release index and image tag are published. A manual build with `push=false` also runs the runtime suite but publishes nothing.
2. Take that digest, or resolve it: `docker buildx imagetools inspect <ref> --format '{{.Manifest.Digest}}'`.
3. Run `scripts/release.sh --runtime-image <ref>@sha256:<digest> --dataset-version 1.4.0 --harbor-src <clean Harbor checkout at the image commit> --loca-src <pinned LOCA-bench checkout>`. Before changing generated files, the script queries the live `origin` remote and requires the clean Harbor source commit to be an ancestor of its `adapters` branch. The local `origin/adapters` tracking ref must match the remote; refresh it with `git -C <harbor-src> fetch origin adapters` before release. Remote lookup failures, stale refs, and unmerged source commits fail closed. The verifier does not fetch or alter Harbor refs. It then pulls the actual image and verifies its baked runtime contract, profile, isolation policy, task-index hash, upstream pin, patch manifest, patchset, and OCI source-commit label against the clean source checkout. It then generates and validates the 525 tasks. Docker must be available; a missing image or a source mismatch fails the release.
4. Review and commit the generated changes, then merge them through the repository's normal review flow.
5. Check out the intended merged release commit, then run `git tag -a v<x.y.z> -m "loca-bench <x.y.z>"`.
6. Publish that tag with `git push origin v<x.y.z>`. Pushing `main` from a feature branch does not publish that branch's generated changes.

Tags are immutable. A corrected release is a new version, never a moved tag.

Before any hardened full run, require the exact candidate image and matching controller to pass the isolation probe and `loca-bench-smoke` on Daytona, plus complete AB preprocessing for all five 256K seeds under the intended sandbox resource limits. Kernel version alone is insufficient. Inspect `loca/environment.log` for generation failures; unresolved failures must remain explicit ungraded coverage, not a claim that the full matrix is ready. Report the context window and output-token budget with the EDL curve. See the adapter README for the full go/no-go checklist.

CI resolves the Harbor checkout from `manifest.adapter.commit`, checks the dataset, then probes the actual pinned image. Historical contract-1 manifests remain valid with their original adapter and image; the new release script requires the hardened contract-2 runtime and the fresh `adapters` ancestry check. Historical image validation without `--require-hardened` does not require network access to the Git remote or release-branch ancestry. Updating the Platform dataset pin and deploying the matching controller are separate release steps after both repositories and the image are ready.

For a local tooling check without Docker, run `python3 -m unittest discover -s scripts -p 'test_*.py'`. This checks the provenance rejection paths; it does not certify a runtime image or the isolation boundary.
